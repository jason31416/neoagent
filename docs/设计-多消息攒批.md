# 设计：多消息攒批（settle）

状态：已实现。起因是产品笔记里的"多消息输入处理"：人说话是连着发的，
"帮我查下明天天气"+"顺便上海的也看看"不该被当成两次独立请求、更不该第二句
把第一句的回复打断重跑两次。

## 一、语义：打断与继续是两件事

- **打断要立刻**：消息一到就入账；若回合正忙，**立即取消在飞的模型请求**——
  止血：不让基于旧理解的话发出去（气泡是回合中途投递的，取消 = 这句之后不再说错话）。
  正在跑的工具**不杀**（杀一半比跑完更糟），跑完即停、不再进下一轮。
- **继续要等窗口**：打断后 agent 原地待命（turn 循环的攒批屏障），
  窗口到点 kick 才带着批内**全部**消息一次重渲染重跑——连补几句只打断一次、只重跑一次。

```
消息到达 ──→ 入账 +（忙时：立刻取消在飞模型）→ 原地待命
              └─ 攒批窗口（判定定档：0 / 4 / 15s，最新一条改判）
窗口到点 ──→ kick：带着批内全部消息，一次重渲染重跑
```

## 二、档位：Jev 单 choice 判定

判定用 Jev（TypeSafe System One 决策模型，不生成文字、只答类型化问题），
**与等待并行**，不加体感延迟；窗口从消息"到达"（入账完成，语音 = 转写完成）起算，
判定回来只改判"还剩多久"。

| 判定 | 含义 | 等待 |
|---|---|---|
| 不会补充 | 明确指令/问题 | 0s（判定一回来就开工） |
| 可能有补充 | 像开了个头 | 4s |
| 话头碎片 | "对了"之类 | 15s |

- 未启用 Jev（没配 key）：固定 3~4s 随机；
- 判定失败：按"可能有补充"档；
- 每条新消息重置窗口（最新一条定档），整批总上限 20s（从批内首条起算）；
- 提示词带具体例子校准档位（见 `core/settle.py` 的 `_QUESTION`）。

接入细节（实测踩坑）：端点 `opencode.ai/zen/v1/systemone`，免费模型
`jev-1.13-free`（限时）；必须带自定义 User-Agent（Zen 403 掉 Python 默认 UA）；
choice 的选项字段叫 `criteria`。封装在 `providers/jev.py`，主动 jev 将来复用。

## 三、落点

- `core/settle.py`：攒批门（按会话独立窗口；指令直通不攒批）；
- `core/agent_loop.py`：`submit` 拆成 `ingest`（预处理+入账+立即打断）与
  `kick`（放行开工）；turn 循环加攒批屏障（`kicked_input_gen`/`kick_event`）；
- `run.py`：`on_message` 走 `gate.push`（频道 + 控制台裸输入同一入口）；
- `config.yml` `settle` 组 + 环境变量 `NEOAGENT_JEV_API_KEY`。

## 四、边界与取舍

- **命令（/ 开头）不攒批**：立即入账执行；
- **已发出的气泡撤不回**：能保证的是"打断这句之后不再说错话"；
- 控制台攒批期间不加任何提示（安静原则）；模型看到没说完的话自己会接
  （不给 M 加"追问"特判——碎片档只是多等一会儿，到点照常开工）；
- 窗口按"会话"（channel+chat）独立，不跟 timeline_bucket 走——
  飞书说话不等微信的批；
- 工具执行不中断：steer 语义保留（跑完即停，下次渲染带上新消息）。
